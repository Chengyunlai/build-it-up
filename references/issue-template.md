# Issue 模板

以下结构是可调整的最低要求。标题尽量使用用户指定的语言，但每个章节的含义都要保留。只有确实不相关时才能省略，并说明原因。

## 标题

使用便于搜索的标题，以分类前缀开头，并包含面向结果的动词：

`[feature|bug|refactor|design|research|chore] verb + object — expected outcome`

避免“新增一个服务”这类只描述实现手段的标题。优先使用“[feature] 在处理前校验上传内容——尽早拒绝无效文件”这类表达。

## 正文

### 背景与问题

谁遇到了问题、现在的行为是什么，以及为什么这个问题重要。

### 期望结果

描述可观察的结果，包括重要的用户、API、数据或运维行为。

### 建议行为

用通俗语言描述正常路径、重要边界情况、错误、权限和状态变化。能够消除歧义时，补充一个小例子。

### 范围

列出包含的工作和明确的非目标。对于有意延期的相关工作，也要点名说明。

### 验收标准

写成可测试的陈述，优先使用：

- 给定某个初始条件，当某个动作发生时，应得到某个可观察结果。
- 不只覆盖成功路径，也要覆盖失败和边界情况。
- 不要使用“运行良好”“足够健壮”这类模糊标准。

### 实现指南

列出可能涉及的代码区域、接口或数据变化、迁移与向后兼容问题，以及一条可逐步验证的实现顺序。仓库相关判断要标记为“已观察到”或“假设”。

### 实现闭环预案

在开始编码前预先写下，完成后必须回填实际结果：

- **目标 example**：example 路径、入口文件或入口测试。
- **最短组装路径**：从公开导入、创建应用和注入依赖，到一次真实输入和输出的调用链。
- **关键断点候选**：入口、组装、核心行为、状态变化和输出位置中适用的断点。
- **验证命令**：一条最小复现命令和预期输入/输出。
- **完成记录**：实现完成后更新的 example 文档、实现记录或设计文档位置。
- **Commit 关联**：完成后回填 commit SHA，并将 issue、example、断点指南和验证证据互相链接。

Example 是理解这次实现的最短入口，不是可选装饰。若仓库没有合适的 example，应在实现范围中加入一个最小 example；若确实无法提供，要记录具体原因和替代的可回放入口。

### 测试策略

将每条验收标准对应到最合适的单元测试、集成测试、端到端测试、手工检查或视觉检查。相关时，补充如何验证与图表绑定的流程。

### 风险与决策

记录风险、考虑过的替代方案、已经选择的取舍，以及仍需要用户决定的事项。

### 图表

链接到评审包中的 Mermaid 代码块；绑定成功后，再补充 draw.io 文档 URL 或路径。图表名称、页面名称或两者都要包含 issue key。

### 实现完成回填

完成代码后补充：

- 实际 example 和最短启动命令。
- 实际断点的文件 + 符号 / 测试名、观察变量和预期变化；不要只写行号。
- 实际执行过的验证命令及结果。
- 完成 commit 的完整 SHA、分支和主要变更文件。
- 实现记录与 example 文档的链接。

## 评审清单

请求确认前，检查以下内容：

1. 标题描述了结果，并且包含分类。
2. 新加入的贡献者不看这段对话，也能理解问题。
3. 验收标准可观察，并覆盖重要的失败路径。
4. 每个图表节点都能在 issue 中找到对应概念。
5. 假设、非目标和待决策项都清楚可见。
6. 实现指南足够具体，可以据此行动，但没有把未知细节伪装成已确定事实。
