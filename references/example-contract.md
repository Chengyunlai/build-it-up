# Example 规范：核心代码与 user_code

每个阶段的 example 必须同时包含两个部分：

1. `core/`：本阶段真正新增或改变的核心代码，以及它解决的问题。
2. `user_code/`：站在使用者角度，通过公开 API 使用这项能力的最短代码。

`user_code/` 是主线，`core/` 是解释主线为什么能够工作。读者和其他 AI 应先打开并运行 `user_code/`，再按需进入 `core/`。不能只展示内部实现通过测试，就把它称为完成的 example。

## 推荐结构

```text
examples/<stage-id>-<slug>/
├── README.md                 # 先说明 user_code，再链接 core 和记录
├── user_code/
│   ├── README.md             # 使用者视角、命令、输入输出、断点入口
│   └── main.*                # 最短可运行调用路径
├── core/
│   ├── README.md             # 核心思想、实现文件和状态变化
│   └── ...                   # 必要时放最小核心源码 / fixture
└── breakpoints.md            # 断点较多时拆出；少时分别写入两个 README
```

如果核心代码已经位于项目的 `src/`、`packages/` 或其他正式目录，不要复制一份产生漂移。此时 `core/README.md` 写清楚本阶段涉及的真实文件、符号和变更 commit；`user_code/` 仍然保留可运行的使用者代码。只有为了隔离教学场景而复制最小核心代码时，才允许把源码放进 `core/`，并标明它与正式代码的关系。

## user_code 的硬性要求

`user_code/` 必须满足：

- 从公开包 / 公开模块导入，不导入内部实现、测试专用入口或相对路径绕过封装。
- 以使用者真实会写的顺序组装：创建入口、提供必要配置或依赖、传入真实输入、得到可观察输出。
- 包含一个具体输入、一个关键结果和一个可复制的运行命令；默认不依赖读者先读 `core/`。
- 暴露的配置、参数和命名应该是使用者真正需要理解的内容；内部状态、适配器和路由细节留在 `core/`。
- 代码保持短、直、可读。不要为了展示内部能力，把调试工具、测试替身、框架对象或多余的基础设施塞进主调用路径。
- README 先解释“使用者写了什么、系统返回什么”，再解释这段代码对应的内部路径。

推荐的使用者主线形状：

```text
公开导入
  → 创建公开入口
  → 传入必要依赖 / 配置
  → 调用一个公开方法
  → 传入具体输入
  → 得到具体输出
```

不要为了追求“看起来短”而隐藏必要概念；清爽不是魔法。使用者必须能看懂每个保留参数为什么存在，以及最终结果如何产生。

## core 的要求

`core/` 不是第二个 user_code，也不是把所有生产源码复制进 example。它要说明：

- 本阶段改变了哪个核心行为、边界或状态。
- `user_code/` 调用的公开入口如何进入核心代码。
- 哪个关键中间结果证明思想已经落地。
- 核心代码的真实路径、稳定符号和对应 C1 commit。
- 哪些复杂度是核心能力本身，哪些复杂度不应该泄漏给使用者。

核心代码如果无法通过 `user_code/` 的公开路径触发，必须说明原因，并把它当作 API / 组装边界的设计反馈，而不是默认接受一条内部测试路径。

## user_code 清爽度是设计验收

完成 example 前，先检查 `user_code/`，再检查 `core/`。以下任一情况都说明实现或公开 API 可能仍有问题：

- 使用者必须导入内部模块、私有类或测试 fixture。
- 使用者必须手工拼接多个本应由公开入口负责的内部对象。
- 使用者必须理解框架内部路由、状态字段、节点名称或适配器协议，才能完成普通调用。
- 使用者代码里出现大量与业务无关的初始化、转换、重复配置或防御性分支。
- `user_code/` 只能通过复制生产代码、修改源码或直接操作内部状态才能得到结果。
- 为了证明功能存在，example 添加了很多旁路代码，导致主调用路径看不出真实使用方式。

发现这些问题时，按以下顺序处理：

1. 确认复杂度是否确实是使用者必须决定的业务概念。
2. 如果不是，回到公开 API、默认配置、依赖注入或组装边界修正实现。
3. 重新编写 `user_code/`，让它只保留使用者需要表达的意图。
4. 再把实现细节、状态变化和断点放回 `core/README.md` 或正式源码说明。

不要用更长的注释、教程或一层 helper 包装来掩盖 user_code 的结构问题。若本阶段明确无法改善，必须在 issue 和阶段完成卡中说明阻塞点、原因和后续动作。

## 验收清单

- [ ] `user_code/` 是第一个运行入口，命令可以独立复现真实结果。
- [ ] `user_code/` 只使用公开 API，并且调用顺序符合使用者心智模型。
- [ ] `user_code/` 能用一段短说明解释每个必要参数和最终输出。
- [ ] `core/` 说明本阶段核心实现、真实源码位置、关键状态和 C1 commit。
- [ ] 可以从 `user_code/` 的公开调用跳到 `core/` 的稳定符号和断点。
- [ ] 如果 user_code 不清爽，已经优先检查并修正公开 API / 组装边界，或明确记录未解决原因。
- [ ] example README、examples 总索引、issue、实现记录和 C1/C2 commit 互相链接。
