# Mermaid 与 draw.io 能力边界和绑定流程

这份规范首先解决“能不能真的驱动 draw.io”的判断问题。Mermaid 能生成、能生成 `.drawio` XML、能打开一个 draw.io URL、能控制浏览器里的 draw.io，以及能实时修改当前打开的 draw.io Desktop 画布，是五种不同能力，不能合并成一句“支持 draw.io”。

## 能力分级

每次任务开始时，先检查当前 Codex 主机实际暴露的工具、已配置的 MCP 和浏览器 / 桌面控制能力，并报告精确等级：

| 等级 | 能力 | 证据要求 | 可以声称 |
| --- | --- | --- | --- |
| D0 | 生成 Mermaid | 已生成可复制、可渲染的 Mermaid 源码 | “可以生成 Mermaid” |
| D1 | 生成或导入 `.drawio` 文件 / URL | 文件实际写入或 URL 实际生成；不要求打开画布 | “可以交付可编辑文件或导入入口” |
| D2 | 打开 draw.io 网页编辑器 | 浏览器工具或 MCP 实际打开页面，并能读取页面状态 | “可以打开网页编辑器” |
| D3 | 实时控制浏览器中的 draw.io 文档 | 已成功连接目标文档，并能读取文档 / 页面 / 元素状态 | “可以修改当前浏览器文档” |
| D4 | 实时控制 draw.io Desktop 当前画布 | 专用 live 工具实际连接 Desktop，并成功读取当前窗口 / 文档状态 | “可以修改当前 Desktop 画布” |

能力是累积的，但 D0/D1 不代表 D2，D2 不代表 D3，D3 更不代表 D4。看到 draw.io 应用正在用户电脑上打开、仓库里有 `drawio-binding.md`、网络上存在某个 MCP 项目，均不是连接成功证据。

## 第一轮必须报告什么

第一张决策卡片中固定使用类似下面的状态，不要写笼统的“支持 draw.io”：

```text
图表能力：
- Mermaid（D0）：已确认可以生成。
- `.drawio` 文件 / URL（D1）：<已确认可生成 / 未确认>。
- draw.io 网页编辑器（D2）：<已打开并读到页面状态 / 未配置 / 未检测到浏览器控制>。
- 浏览器画布实时控制（D3）：<已连接目标文档 / 只有打开能力 / 未检测到 live 工具>。
- draw.io Desktop 实时控制（D4）：<已连接当前窗口 / 未检测到 Desktop live 工具 / Desktop 连接失败>。
- 当前可以交付：<Mermaid、XML、可编辑文件、网页文档或实时修改中的准确范围>。
- 当前不能声称：<没有成功探测到的能力>。
```

能力报告只是告知，不要因为能力不足连续追问用户。只有用户明确要求实时控制，而当前等级不够时，才提出一个阻塞选择：配置可用桥接、交付可编辑文件，或接受 Mermaid / 手工导入降级。

## 真实探测协议

### 1. 先检查工具，不先检查“理论方案”

优先查看当前运行环境是否真的暴露以下任一种能力：

- draw.io 专用 MCP 工具（例如 capabilities、document、page、element、save 等操作）。
- 已配置并可调用的标准 draw.io MCP server。
- 应用内浏览器控制工具，并且能打开和读取 `app.diagrams.net`。
- 桌面控制工具，并且能识别 draw.io Desktop 的当前窗口。
- 本地文件读写能力，用于交付 `.drawio` / XML；这只能证明 D1。

如果工具列表里没有对应能力，不得因为网上有安装教程、某个插件仓库存在，或用户已经打开应用，就报告“已连接”。

### 2. 探测必须有成功回读

不能把“发出打开命令”当作“已经驱动”。每次升级能力等级至少要完成一次无歧义的回读：

```text
生成文件：文件存在，并能读回合法 XML / 文件路径。
打开网页：页面确实打开，并能读到 URL、标题或可识别的 draw.io 状态。
连接浏览器文档：读到目标文档 ID / 页面名 / 当前状态。
连接 Desktop：读到当前窗口或文档状态，并确认后续写操作的目标。
执行修改：修改后再次读取或截图验证，确认目标节点、标签、连线或页面真的变化。
```

若探测失败，保留失败证据和失败层级，例如“D1 成功，D2 未配置；因此已交付 XML，未声称打开网页”。不要把失败隐藏为“稍后可以同步”。

## 方案与宿主限制

不同方案解决的问题不同，使用前先确认它属于哪一级：

| 方案 | 典型能力 | 不能据此声称 |
| --- | --- | --- |
| 官方 [`jgraph/drawio-mcp`](https://github.com/jgraph/drawio-mcp) MCP App | 在支持 MCP Apps 的宿主中提供交互式图表组件 | Codex / ChatGPT 一定能内嵌显示；也不等于控制 Desktop |
| 官方 [`@drawio/mcp`](https://www.npmjs.com/package/@drawio/mcp) Tool Server | 通过标准 MCP 生成内容并打开浏览器编辑器，可处理 XML / Mermaid | 修改已经打开的任意画布；必须先在当前 MCP 宿主配置并成功探测 |
| 官方 draw.io Codex CLI 插件 | 生成 / 打开原生 `.drawio` 文件或导出结果 | Codex Desktop 能安装 CLI 插件，或能实时修改 Desktop 窗口 |
| `lgazo/drawio-mcp-server` + 浏览器扩展 / `--editor` | 社区方案，可实时操作浏览器版或自托管编辑器 | 已经能控制 draw.io Desktop；其文档明确存在 Desktop CSP 限制 |
| 社区 Desktop live 插件 | 某些环境可通过本地调试通道控制 Desktop graph/model | 官方支持、跨机器可用或当前环境已安装；必须实际探测 |
| 官方 Embed mode + 自建 bridge | 控制自己创建的 `embed.diagrams.net` iframe | 控制原生 Desktop 或用户已经打开的任意 draw.io 页面 |
| Playwright / 坐标点击 | 辅助打开页面或少量 UI 操作 | 可靠地控制 canvas 图模型；它只能作为最后手段 |

当前 Codex Desktop 不应默认被当成 Codex CLI。尤其要注意：MCP App 能力、标准 stdio MCP、Codex CLI 插件、应用内浏览器控制和 Desktop live 调试通道是不同的集成面。只有当前宿主真正加载并暴露对应工具时，才能使用该方案。

## 用户要求绑定时的执行顺序

用户确认方案并明确要求绑定 draw.io 后，按以下顺序执行：

1. **锁定目标**：确定 issue key、图表身份、目标宿主（网页 / 浏览器现有文档 / Desktop 当前画布）和目标文件；目标不明确时只问一个必要问题。
2. **读取状态**：优先读取已有文档、页面、文件或窗口状态；不要直接覆盖，也不要默认创建新文档掩盖“现有画布连接失败”。
3. **选择最低可行能力**：只生成文件用 D1；需要打开网页用 D2；需要改已有浏览器文档用 D3；需要改 Desktop 当前画布才要求 D4。不要用 D1 的结果冒充 D3/D4。
4. **先做无害试写**：在确认目标后执行一个可识别的小修改（例如新增带 issue key 的标题或测试节点），然后回读状态或截图验证修改确实落在目标文档。
5. **执行完整导入 / 修改**：导入或重建已经确认的 Mermaid 图，使用 issue key 和分类命名文件、页面或图表；保留 Mermaid 源码作为事实基准。
6. **回读验证**：再次读取页面 / 元素 / 文件，或进行视觉检查，确认节点、标签、连线、页面和布局实际存在。
7. **互链记录**：将 issue URL/key 写入图表说明（如果客户端允许），把真实 draw.io URL 或本地路径回填 issue / 实现记录，并记录实际能力等级和验证方式。

任何一步失败，都停在已证实的等级，报告“已完成 / 未完成 / 需要用户配置”的边界。不要继续发出一串没有能力基础的操作指令。

## 网页版与 Desktop 的具体规则

### 网页版

浏览器控制工具可用且已经通过 D2/D3 探测时：

- 优先使用文档 / 页面 / 图模型接口或 draw.io 的导入协议，不使用脆弱的坐标点击。
- 连接现有文档前先列出或读取目标文档，避免修改错标签页。
- 如果只能打开 `app.diagrams.net` 而不能读取图模型，能力最多报告为 D2。
- 页面打开后没有成功回读，不得报告“网页图已创建”。

### Desktop

Desktop 实时控制只有在专用工具成功连接并回读当前窗口 / 文档后才报告 D4。普通桌面自动化、能点击应用图标、能看到 Desktop 窗口，都不等于 D4。

不要把浏览器扩展的 localhost WebSocket 方案当成 Desktop 方案。draw.io Desktop 的 CSP 可能阻断这类连接；不要把关闭安全策略、修改应用包或放宽 CSP 作为默认操作。若用户确实选择第三方 Desktop live 插件，先说明它是社区方案、需要本地连接和权限审查，并先在测试文件做无害试写。

## 降级交付

当用户想要 draw.io，但当前环境没有足够控制能力时，直接给出可执行的降级结果：

1. Mermaid 渲染图和完整源码。
2. 可选的 `.drawio` XML 文件或压缩 URL（如果 D1 可用）。
3. 建议文件名 / 页面名：`<issue-key>__<category>__<short-title>`。
4. 在 draw.io 网页版中导入 Mermaid / XML 的最短手工步骤。
5. issue 与图表互链需要手工完成的具体位置。
6. 明确写出“当前未驱动 draw.io”的原因和可继续的最短配置路径。

降级交付不是失败隐瞒：如果只完成 Mermaid，就明确标为 D0；如果只写出 `.drawio` 文件，就明确标为 D1。不要输出一个看似完整但实际没有图表文件、链接或修改结果的“绑定完成”摘要。

## 统一身份与记录

只有 issue 获得明确确认并成功发布后，才能使用 issue key 作为图表身份：

`<issue-key>__<category>__<short-kebab-case-title>`

在 issue、Mermaid、`.drawio` 文件、页面名和实现记录中尽量复用同一身份。绑定记录至少保存：

- 实际能力等级（D0–D4）。
- 使用的宿主和工具 / MCP 名称。
- 探测和回读证据。
- 真实文件路径或 URL；本地路径不能伪装成分享链接。
- issue key、图表分类、页面名和 C1/C2 commit。
- 未完成的控制步骤及用户下一步需要做什么。

确认前，Mermaid 源码是事实基准；绑定后也必须保留。若 tracker 或 draw.io 不支持双向链接，记录单向链接和限制，不要声称互链已经建立。
