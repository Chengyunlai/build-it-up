# 决策卡片协议

决策卡片是人与 AI 建立共识时的主要交互单位。它的目标不是展示 AI 已经想了多少，而是让人一眼知道：当前进行到哪里、现在只需决定什么、这个选择会带来什么具体结果。决策卡片默认是“具体场景图先于文字”的视觉交互，不是缩短后的文字报告，也不是下一轮追问的借口。

## 适用范围

本协议用于尚有高影响选择的新需求。已确认范围内的图型、排版、文字修正直接执行；解释或评估问题直接回答。不要为了套卡片而发明问题、强制画图或创建 issue。图型验收以 [diagram-selection.md](diagram-selection.md) 为准。

## 每轮固定结构

除非用户主动要求完整方案，每轮按下面顺序输出，并控制在能快速扫读的长度：

```text
当前阶段：<探索问题 / 确定目标 / 选择载体 / 确定行为 / 形成方案>

一句话目标：<这次要解决什么>

图表能力：
- Mermaid：<可用性>
- draw.io 网页版 / 桌面版：<实际检测结果>
- 当前可交付：<直接完成什么，哪些需要手工>

现在只需要决定：<一个且只有一个决定>

一眼看懂：
<一张或几张由 AI 自动选择类型的具体场景图>

我的推荐：<推荐选项>

原因：
- <与当前仓库或需求直接相关的理由>
- <推荐方案带来的验证价值或代价>

本轮暂不决定：<明确列出 1–3 个容易让人分心、但还没轮到的事项>

请回答：<一个明确的问题>
```

“请回答”只能包含一个问题。需要多个决定时，拆成多轮；不要在一个问题后面追加“同时确认 A、B、C”。“图表能力”只是状态告知，不是额外问题。图必须出现在推荐理由之前或紧邻推荐理由的位置，让用户先看到关系，再阅读解释。

## 展示规则

1. **先给结论位置，再给解释**：第一屏必须出现“当前阶段”和“现在只需要决定”。不要先写长背景。
2. **具体图先于长文**：每张卡片至少有一张与当前问题匹配的图；复杂问题最多给三张互补图。图的类型由 AI 根据问题选择，不把“请指定流程图还是架构图”变成用户负担。
3. **先说人话，再说术语**：先描述用户能观察到的行为，再给项目术语。例如“用户想做的事情（后续称为 Intent）”，不要直接把 `Intent` 当成已知概念。
4. **先给最小模型**：图表只展示当前决策所需的节点。通常使用 3–8 个主要元素；尚未确认的对象标为“待定”，不要为了完整而臆造。
5. **按图型给证据**：流程图和时序图呈现输入、处理与结果；架构图呈现层级、归属、边界与关键依赖；类图呈现属性、方法与标准关系。不要将输入输出要求套到所有图。
6. **避免空泛**：行为图展示实际处理；结构图展示真实模块、类和关系。不要只画“目标 → 方案 → 好处”。
7. **按问题选图**：顺序问题用流程图或时间线，协作问题用时序图或组件图，状态问题用状态图，范围问题用分层图或对比图，数据问题用 ER 图或数据流图。不要为了统一而所有问题都画流程图。
8. **图下只解释关系**：只补充箭头、边界、状态变化或方案差异中不可直接从图上读出的事实，不再重复整段背景。
9. **让图直接表达选择**：比较方案时在图中显式标出“推荐”与“备选”；范围问题区分“本阶段”与“后续 / 暂不包含”；流程或状态问题标出当前所在位置。用户只看图，也应能大致知道推荐方向。
10. **名称符合视角**：流程节点用动作，架构节点用模块名称与职责，类图使用真实类型名。无需将类型名改写成动作句。
11. **推荐必须带代价**：推荐一个选项时，同时说明它为什么适合当前目标，以及它暂时不解决什么。
12. **一次只推进一层**：用户询问一个词、一个节点或一个取舍时，只解释该点，然后回到当前决策。
13. **完整内容延后**：完整 issue、长 Mermaid、详细实现顺序、风险清单和测试矩阵，在关键决策稳定后再生成。
14. **不要把示例当产品**：如果使用 Todo、登录、订单等领域作为验证载体，明确标注“示例 / 验证载体”，并说明它为什么足够小、可以替换。
15. **图必须有可识别的任务名**：在 draw.io 画布底部放置根据当前任务生成的名称，包含具体主题、图型和阶段 / issue 标识；Mermaid 源码同步保留名称注释或渲染后的图下注释。不要用“流程图”“架构图”作为唯一名称。具体格式见 [diagram-selection.md](diagram-selection.md)。

## 何时结束提问

决策卡片不是问卷。用户确认主要方向后，检查四件事：目标是否清楚、范围是否足够、具体场景和结果是否存在、剩余未知项是否只是低风险实现细节。四项满足时，直接进入方案卡片或下一步行动。

不要因为还可以继续讨论命名、目录、语言、测试组织或每一个边界，就继续向用户提问。把这些内容作为“AI 采用的假设”列在方案中；只有它们会改变产品方向、外部行为或验收标准时，才重新开一张决策卡片。

## 适合使用的最小图

当流程关系有助于理解时，只画当前问题需要的最小流程。实际执行时，图型由问题决定，不必固定使用流程图：

```mermaid
flowchart LR
    Input[用户输入] --> Meaning[系统理解的用户目标]
    Meaning --> Decision[当前要决定的方案]
```

如果用户还不理解节点含义，先用文字解释，不要继续增加节点。

## 具体场景图示例

当需要说明“做一个 Todo 验证应用到底会发生什么”时，优先画一次真实操作，而不是画抽象的目标和选择：

```mermaid
sequenceDiagram
    actor User as 终端用户
    participant App as Todo 应用
    participant Graph as 执行流程
    participant Store as 任务记录
    User->>App: 输入 `add 买牛奶`
    App->>Graph: 识别为“新增任务”
    Graph->>Store: 创建任务 #1「买牛奶」
    Store-->>Graph: 返回未完成任务 #1
    Graph-->>App: 生成执行结果
    App-->>User: 显示「已添加 #1：买牛奶」
```

这张图具体说明了四件事：用户输入什么、系统经过哪些步骤、数据发生了什么变化、用户最后看到什么。它比“验证应用 → 尽快获得证据”更能帮助用户判断这个方案是否真的符合自己的理解。

如果还需要说明验证边界，再补一张覆盖图，明确哪些能力会被这次操作验证，哪些能力不在本阶段：

```mermaid
flowchart TB
    Input[输入 `add 买牛奶`] --> Parse[解析用户输入]
    Parse --> Route[选择新增任务路径]
    Route --> Store[保存任务记录]
    Store --> Output[输出「已添加 #1：买牛奶」]
    Route -.验证.-> PublicAPI[公开 API]
    Store -.验证.-> Dependency[构造时依赖注入]
    Output -.验证.-> Entrypoint[终端入口]
    Future[数据库、Web 页面、外部模型] -.本阶段不验证.-> Boundary[后续范围]
```

上述是行为图示例，输入输出要求不适用于架构图和类图。结构图的元素与关系同样必须来自需求或源码；不能为填满布局虚构组件。

## 图的选择示例

如果当前问题是“先做小验证应用还是完整框架”，用范围图标出本阶段的终端入口、公开 API 和内存存储，以及后续的 Web 入口和持久化适配；也可以复用上面的具体操作图说明验证证据。

不要用“目标 → 选小方案 → 反馈快 / 选大方案 → 成本高”代替图示。这只是论点排版，没有提供组件边界或行为证据。结构、对象关系和调用顺序的标准示例见 [diagram-examples.md](diagram-examples.md)。

## 从卡片进入完整 issue 的条件

只有同时满足以下条件，才进入完整 issue 草案：

- 用户已经逐个确认了影响范围的关键决策。
- 关键术语已经用自然语言解释，并且用户没有继续提出概念歧义。
- 正常路径、至少一个重要失败路径和非目标已经明确。
- Mermaid 图中的主要节点可以在 issue 中找到对应概念。

图表能力不构成额外确认条件。即使当前只能生成 Mermaid，也可以进入完整 issue；draw.io 绑定作为已报告能力状态下的后续交付或手工交接。

代码实施完成后，如果用户此前明确要求过实现，使用独立的“阶段完成卡”可选流程；不要把关键路径汇报重新混入需求决策卡，也不要借阶段汇报继续追问下一阶段。

进入完整 issue 后，先给“最终共识卡片”，再给完整 issue。最终共识卡片只保留目标、已确认决策、范围、验收标准摘要和下一步动作，避免人再次从长文中寻找结论。
